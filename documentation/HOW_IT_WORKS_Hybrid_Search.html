Hybrid search: dense + keyword, fused

Hybrid search (dense + keyword/BM25-style, merged via Reciprocal Rank Fusion) is the biggest bang-for-the-buck upgrade to RAG11's retrieval, because pure embeddings often miss exact numeric/terminology matches — like 0.8 g/kg RDA — that a plain keyword search nails instantly. Postgres full-text search (tsvector) pairs naturally with the pgvector table RAG11 already has, so no new database or search service is needed.

2 search methods, 1 fused ranking
RRF k = 60
tsvector + GIN index
0 new services — same Postgres table
Composable with rerank
Motivation

The problem in plain terms

Your current search only compares "meaning vectors." It's great at "this is roughly about the same topic" but bad at "this contains the exact number/word I need."

Example:

Question: "How many grams of protein per kilogram of body weight does the RDA recommend?"
  • Pure vector search might return chunks that are all about protein — muscle building, protein sources, amino acids — but the one chunk that literally says "0.8 g/kg/day" might rank 6th, because a paragraph about "protein timing for athletes" sounds more similar overall.
  • A keyword search for "0.8" or "RDA" would instantly find the exact chunk, because it's just matching text, not meaning.
  • Hybrid = do both searches, then combine the two ranked lists (e.g. "chunk A was #1 in vector search and #3 in keyword search → give it a combined score"). This catches cases where the right chunk scores well on one method but not the other.
Vector search"Find me something in the same neighborhood."
Keyword search"Find me the exact house number."

How hybrid search fits the pipeline

One question triggers two independent, cheap searches over the same rag11_chunks_child_table — one over embedding (dense/semantic), one over chunk_tsv (keyword/lexical). Their ranked lists are merged with Reciprocal Rank Fusion before anything is shown to Claude — and, optionally, before Voyage's reranker narrows the fused list further.

Both searches over-fetch a wide pool first (max(match_count × 4, 15) each — the same "cast a wide net cheaply" pattern rerank already uses) so a chunk only one method would rank highly still gets counted before RRF trims down to match_count.

🔵 Dense (vector) search

Embeds the question and every chunk into the same 1024-dim space, then ranks by cosine distance. Fast, and great at "this is topically related" — but the question and each chunk were embedded completely independently, so it's a rough proxy for "actually answers this."

retrieve_chunks(question) → sorted by cosine_distance ascending

🟢 Keyword (full-text) search

Matches literal words/numbers in the text via Postgres' tsvector, ranked by ts_rank_cd. Finds an exact term or figure reliably, but has no notion of synonyms or paraphrase — "0.8 g/kg" and "0.8 grams per kilogram" don't automatically match.

retrieve_chunks_keyword(question) → sorted by text_rank descending
Reference

Reciprocal Rank Fusion — the merge step

RRF combines two independently-scaled rankings (cosine distance and ts_rank_cd are not comparable numbers) without ever comparing their raw scores directly — it only looks at each chunk's position in each list.

rrf_score(chunk) = Σmethod 1 / (k + rankmethod(chunk))     k = 60

Worked example, using the RDA question above — the chunk with the literal "0.8 g/kg/day" ranks #6 by embedding similarity but #1 by keyword match:

ChunkDense rankKeyword rankRRF scoreFused rank
"…the RDA is 0.8 g/kg/day…"611/66 + 1/61 = 0.0316#1
"…protein timing for athletes…"1—1/61 + 0 = 0.0164#2
"…protein food sources overview…"2—1/62 + 0 = 0.0161#3

The chunk both methods can reach — even from very different ranks — still out-scores a chunk only one method liked, which is exactly the "chunk A was #1 in vector search and #3 in keyword search → combined score" behavior hybrid search is built for. What changed in the schema and API

One additive, idempotent migration (sql/create_sql_tables.sql) adds the keyword-search counterpart to every dense-search piece that already existed — same shape, same table, nothing removed or renamed.

Python API

# low-level: run either search on its own
from reusable_code import retrieve_chunks, retrieve_chunks_keyword, reciprocal_rank_fusion, hybrid_search

dense    = retrieve_chunks("How many g/kg of protein does the RDA recommend?")
keyword  = retrieve_chunks_keyword("How many g/kg of protein does the RDA recommend?")

# merge any number of ranked lists via RRF -- generic, not hybrid-search-specific
fused = reciprocal_rank_fusion({"dense": dense, "keyword": keyword})

# or just do the whole thing in one call (what ask_question uses):
chunks = hybrid_search("How many g/kg of protein does the RDA recommend?", match_count=5)

# end-to-end, composes with reranking:
from reusable_code import ask_question
result = ask_question("...", use_hybrid=True)                    # hybrid retrieval only
result = ask_question("...", use_hybrid=True, use_rerank=True)   # hybrid, then reranked
