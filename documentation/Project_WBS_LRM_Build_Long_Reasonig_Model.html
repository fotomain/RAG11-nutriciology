Building a Long-Reasoning Model (LRM) on top of RAG11

This WBS plans the work to give RAG11 a long-reasoning answer mode — one that plans, checks its own claims against retrieved evidence, and handles multi-hop or comparative nutrition questions (the kind retrieve_chunks_multi_query() already detects) — without breaking the RAG11 pipeline that already works today. "LRM" here means a reasoning-specialized capability, built either as an orchestration layer over Claude's existing extended thinking, or — if the numbers justify it — as a fine-tuned/distilled model. The plan is written to make that choice with evidence, not in advance.

The recommended path, in one paragraph

Build the orchestration-layer LRM first. Only train a model if it earns it.

RAG11 already has the hard part of "reasoning" solved at the data layer: hybrid search, HyDE, multi-query splitting, reranking, and parent-chunk expansion are all retrieval tools. The fastest, cheapest, lowest-risk way to get long-form reasoning is to let Claude call those tools in a loop — plan, retrieve, draft, self-check against citations, revise — using Claude's own extended thinking. That is Phase 3A below. It needs no training data, no GPU budget, and no change to a single line of reusable_code/. Training a fine-tuned/distilled reasoning model (Phase 3B) is real, and included in this plan, but it is gated behind Phase 4's evaluation numbers — build it only if the orchestration layer's own eval scores show the investment is worth it, not because a bigger roadmap sounds more impressive.

Two build paths, compared

Orchestration layer vs. fine-tuned/distilled model

Both are in scope. The WBS sequences them so path A de-risks and generates the training data path B would need.

Path A — v1 Reasoning orchestration layer

  • Claude + extended thinking, calling RAG11's existing retrieval functions as tools
  • Ships in weeks; no GPU budget; no training-data licensing exposure
  • New, additive function — e.g. ask_question_deep() — RAG11's ask_question() is untouched
  • Self-checks claims against retrieved chunk text before finalizing an answer

Path B — v2, conditional Fine-tuned / distilled LRM

  • LoRA/QLoRA fine-tune of an efficient open-weight reasoning-capable base model
  • Trained on chain-of-thought traces generated by Path A (Phase 2) — not hand-written
  • Only started after Phase 4's go/no-go gate says Path A's ceiling is worth beating
  • Requires textbook-licensing legal review before any weights are trained (§ Risks)
Hard constraint

"RAG11 must work also" — treated as an enforced invariant, not a promise

Why this needs mechanism, not good intentions

RAG11 already has a green test suite (test_reusable_code.py), a working notebook pipeline (Stage 1.0 → 1.9 → 2), and a documented public API (ask_question() and friends in reusable_code/). The risk isn't that someone decides to break it — it's that an LRM change quietly does, because reasoning-layer work and retrieval-layer work touch the same functions.

  • API freeze: reusable_code/ only ever receives additive changes (new optional kwargs, new modules) for the duration of this project — never a changed signature or return shape on ask_question(), retrieve_chunks(), hybrid_search(), etc.
  • CI gate: every PR touching reusable_code/ or the new LRM package runs test_reusable_code.py (fully mocked, no network) and must pass before merge.
  • Smoke test: a scheduled run of stage2_ask_examples1.ipynb-equivalent questions against a real (scratch) Supabase project, so "RAG11 still answers nutrition questions correctly end-to-end" is checked, not just unit-mocked.
  • Separate package: all LRM code lives in its own module (e.g. reusable_code/reasoning.py or a top-level lrm/ package) that imports reusable_code as a dependency and calls its public functions as tools — it never forks or duplicates retrieval logic.

Best recommendations

Ten concrete recommendations

  1. Start with the orchestration-layer LRM (Phase 3A), not a trained model. It ships in weeks, needs no GPU budget, and reuses 100% of RAG11's existing retrieval toolkit as reasoning tools.
  2. Treat RAG11 as the LRM's evidence substrate — never let it bypass RAG11's retrieval. Every reasoning step should ground itself in retrieve_chunks()/hybrid_search()/expand_to_parent_chunks() output; that is what keeps citations real instead of the model reasoning "from memory," which is dangerous in a clinical nutrition domain.
  3. Make "RAG11 keeps working" a CI-enforced invariant, not a promise. Wire test_reusable_code.py plus a smoke-test notebook run into required CI checks on every PR that touches reusable_code/ or the new reasoning package.
  4. Only invest in fine-tuning (Path B) if Phase 4's eval numbers justify it — and even then start with LoRA/QLoRA on an efficient open-weight model, not a full pretrain or full fine-tune. A few thousand QA traces cannot support pretraining and would be wasted on it.
  5. Resolve textbook licensing before any weights are trained on their derived text. Retrieval-time citation use and training-data use are different rights — this is the single biggest legal risk in the plan and belongs in Phase 0/3B.1, not discovered after a model is already trained.
  6. Extend grounding_words() into a scored groundedness metric instead of inventing a new one — it is already the project's existing concept of "what the answer shares with its sources," and promoting it from a debug helper to an eval metric is small and high-leverage.
  7. Add a mode router (fast = RAG11 today, deep = LRM), defaulting to fast. Long reasoning is slower and costs more tokens; make it opt-in per question rather than a blanket replacement of the system that already works.
  8. Require a clinician/nutrition-credentialed reviewer to sign off on sampled LRM outputs before any production launch. This is a health-information system — "sounds confident" is not the same as "is safe to publish."
  9. Keep all LRM code additive, in its own package. Never edit reusable_code/ in place except with new, optional functions — this single discipline prevents most accidental regressions to a codebase that has passing tests today.
  10. Let the Phase 4 go/no-go gate — not the roadmap — decide whether Path B gets built. If the orchestration layer already clears the accuracy/groundedness bar, don't fine-tune a model just because it was on the plan.
