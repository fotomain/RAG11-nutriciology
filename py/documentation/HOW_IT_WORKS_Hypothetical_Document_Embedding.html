HyDE: embed the hypothetical answer, not the question

Hypothetical Document Embeddings (HyDE) asks Claude to draft a short, plausible-sounding textbook paragraph that would answer the question, then embeds that paragraph — not the bare question — and searches with it instead. It closes the "shape of English" gap between a short interrogative question and the long, declarative, technical prose real chunks are written in, so retrieval lands closer to chunks that actually answer the question rather than ones that are merely on-topic.

1 extra Claude call per question
0 schema changes — same dense RPC
input_type = document, not query
Composable with rerank + expansion
Motivation

The problem in plain terms

A question and an answer are written in different "shapes" of English. Questions are short and interrogative; textbook answers are long, declarative, and technical. Embedding the raw question sometimes doesn't line up well with embeddings of the answer-shaped text already sitting in the database.

Example:

Question: "Does drinking coffee before exercise dehydrate you enough to hurt performance?"
  • Instead of embedding that question directly, first ask Claude: "Write a short hypothetical textbook paragraph that would answer this question." Claude might generate something like: "Caffeine has a mild diuretic effect, but studies show that moderate pre-exercise caffeine intake does not cause clinically significant dehydration or impair endurance performance in habituated users…"
  • Embed that fake paragraph instead of the question, and search with it.
  • Why it helps: that paragraph is written in the same style/vocabulary as the real textbook chunks ("diuretic effect," "habituated users"), so it's more likely to land near the actual correct textbook paragraph in vector space than the bare question would.
Bare question"Where's the fiber book?" — a request, not a match.

How HyDE fits the pipeline

One question triggers one extra, cheap Claude call before retrieval even starts. The resulting hypothetical paragraph is embedded on the document side of Voyage's asymmetric embeddings (matching how the real child chunks were embedded in Stage 1.2) and searched with, via the exact same dense RPC plain retrieval already uses.

Unlike hybrid search, HyDE doesn't over-fetch a wide pool and fuse two rankings — it changes what gets embedded before the single dense search call, so it composes with reranking and parent-chunk expansion exactly like plain retrieve_chunks() does. It is not combined with hybrid search here — hybrid's dense half always embeds the raw question (see HOW_IT_WORKS_Hybrid_Search.html).

🔵 Bare-question embedding (default)

Embeds the question itself with input_type='query'. Fast — one embedding call — but a short interrogative sentence and a long declarative textbook paragraph don't always sit close together in embedding space, even when the paragraph is the right answer.

retrieve_chunks(question) → embeds question directly

🟣 HyDE embedding (optional)

Claude first drafts a short hypothetical answer paragraph, which is embedded with input_type='document' instead — the same asymmetric side the real child chunks were embedded on. One extra (cheap, short) generation call, in exchange for a retrieval probe written in the corpus's own register.

retrieve_chunks_hyde(question) → embeds the generated paragraph
Why it matters

Benefits, by audience

The same mechanism reads differently depending on who's asking — a stakeholder cares about answer quality on hard questions; an engineer cares about what changed under the hood and what it costs.

📈 For stakeholders

  • Better answers on "explainy" questions. Questions phrased casually ("does coffee mess with your workout?") retrieve as well as ones already phrased in textbook language ("what is the physiological effect of caffeine on hydration status?") — users don't have to learn to "talk like the textbook" to get a good answer.
  • No new infrastructure. Zero new tables, indexes, or services — it reuses the exact same search LRM11 already runs, so it ships without a migration or a review of new attack surface.
  • Toggle-able, low-risk rollout. use_hyde=True is off by default; it can be A/B tested per question type without touching the existing default path at all.
  • One extra short Claude call per question. The added latency/cost is one small (~200-token) generation call — worth knowing when estimating per-question cost for a rollout.

🛠️ For AI engineers

  • Fixes an asymmetric-embedding blind spot. input_type='query' vs. 'document' narrows the question/answer gap but can't erase it — HyDE sidesteps the gap entirely by embedding document-shaped text on the document side, for both sides of the comparison.
  • Composable, not a replacement. retrieve_chunks_hyde() returns the exact same row shape as retrieve_chunks(), so rerank_chunks() and expand_to_parent_chunks() work on its output unchanged.
  • The hypothetical paragraph is a retrieval probe only. It is never shown to the user and is not fact-checked — the real, grounded answer still comes from Claude reading the retrieved excerpts, exactly as before.
  • Best where hybrid search doesn't apply. Hybrid search's keyword half already rescues exact-term questions ("0.8 g/kg RDA"); HyDE instead helps conversationally-phrased or indirect questions where no exact term exists to key off of in the first place.
Reference

What changed in the schema and API — nothing, structurally

Unlike hybrid search (one additive migration for full-text search), HyDE needs zero schema or index changes. It calls the exact same match_lrm_chunks RPC plain retrieve_chunks() already uses — the only thing that changes is what text gets embedded before that call.

Python API

# low-level: draft the hypothetical paragraph yourself, inspect it, then embed it
from reusable_code import generate_hypothetical_document, embed_hypothetical_document

hypothetical_doc = generate_hypothetical_document("Does drinking coffee before exercise hurt performance?")
embedding        = embed_hypothetical_document(hypothetical_doc)  # input_type='document'

# or just do the whole thing in one call (what ask_question uses):
from reusable_code import retrieve_chunks_hyde

chunks = retrieve_chunks_hyde("Does drinking coffee before exercise hurt performance?", match_count=5)

# or, to also see the hypothetical paragraph that was used:
chunks, hypothetical_doc = retrieve_chunks_hyde(
    "Does drinking coffee before exercise hurt performance?",
    return_hypothetical_document=True,
)

# end-to-end, composes with reranking and parent-chunk expansion:
from reusable_code import ask_question
result = ask_question("...", use_hyde=True)                                   # HyDE retrieval only
result = ask_question("...", use_hyde=True, use_rerank=True)                  # HyDE, then reranked
result = ask_question("...", use_hyde=True, expand_to_parents=True)           # HyDE, then parent-expanded

See py/ipynb/stage2_ask_examples5_hypothetical_document_embedding.ipynb for worked examples, and py/reusable_code/README.md for the full guide. use_hyde is ignored when use_hybrid=True is also passed to ask_question() — hybrid search's dense half always embeds the raw question, so combining the two isn't wired in.
