LRM ER Model

Four tables behind the LRM (Language Reading Model) pipeline: a page-image book viewer with retrieval on top. Full schema in sql/create_lrm_tables.sql.

Diagram

Arrows point from the referenced (parent) table to the table holding the foreign key.

Tables

TableGrainKey relationships
lang lrm_language_table One row per supported language code Reference table, not part of the rowGUID pattern. Every language column elsewhere is a FK to code here — adding a language is one insert, no schema change.
src lrm_source_table One row per (book, language) pair rowOwnerGUID = rowGUID (a source owns itself); rowParentGUID always null (nothing sits above a source).
page lrm_page_table One row per recognised/translated page Both rowOwnerGUID and rowParentGUID point at the owning source — a page sits directly under its source, one level, no separate "section" concept.
chunk lrm_child_chunk_table One row per embeddable chunk of page text rowOwnerGUID is the source; rowParentGUID is the owning page. Usually one chunk per page — a page only splits into more when its text exceeds the embedding token budget.

Why 2 levels, not 3

A RAG pipeline chunking raw PDFs typically needs source → parent-chunk → child-chunk, because a raw source has to be split into sections first. LRM already has that unit: lrm_page_table is naturally page-sized and holds the full page text (rowJSON.text), so it plays the "parent" role as-is. lrm_child_chunk_table only needs to be the child/embedding level: page → one or more chunks.

Retrieval

Three RPCs in sql/create_lrm_tables.sql read lrm_child_chunk_table: match_lrm_chunks (cosine vector search over embedding), match_lrm_chunks_keyword (full-text search over chunk_tsv), and get_lrm_page (expand a matched chunk back to its full page via rowParentGUID). Both search RPCs accept an optional filter_owner (restrict to one source) and filter_language (restrict to one language).

Data dictionary (IFLA LRM)

Three more tables — lrm_definition_table, lrm_definition_attribute_table, lrm_entities_relations_table — form a self-describing metadata layer grounded in the IFLA Library Reference Model (the 2017 bibliographic conceptual model published by IFLA — a different "LRM" from this project's own name, not the page-viewer). They document the four content tables above rather than replacing them: this system doesn't yet need separate Work/Expression/Manifestation/Item tables, so they're a governed data dictionary and standards-mapping layer instead of a schema migration.

TableGrainPurpose
lrm_definition_table One row per concept (not per instance) Catalogs IFLA LRM's 11 entities (Res, Work, Expression, Manifestation, Item, Agent, Person, Collective Agent, Nomen, Place, Time-span) plus this project's own internal concepts (source, page, chunk, language), each with a definition and, where implemented, which physical table it maps to.
lrm_definition_attribute_table One row per (entity, attribute) The data dictionary: every attribute a definition has, its data type, required/repeatable flags, and — when built — which real column carries it. A null maps_to_column is a documented-but-not-yet-implemented attribute (e.g. Manifestation.carrier_type), so extending the model is one insert here, the same "add a row, not a migration" pattern lrm_language_table already uses for languages.
lrm_entities_relations_table One row per typed edge, of two kinds relation_kind = 'external_mapping': schema-level, e.g. expression.language ↔ Dublin Core's dc:language. relation_kind = 'association': instance-level, a real many-to-many link between entities that are peers, not parent/child (e.g. a Work and its Agent). Polymorphic by design (source_type/target_type can name any definition or table), so source_ref/target_ref are free-text identifiers rather than strict foreign keys.
