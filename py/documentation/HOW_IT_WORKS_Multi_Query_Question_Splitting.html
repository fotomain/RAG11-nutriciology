Multi-query / question splitting: one search, many directions

Multi-query / question splitting asks Claude whether a question secretly bundles more than one independent information need — a comparison, a list of distinct topics — and if so, splits it into self-contained sub-questions before retrieval, searches each one separately, and fuses every resulting ranked list back into one with the same Reciprocal Rank Fusion that already merges dense + keyword search. No new table, index, or migration is needed — this is a pure query-time step that adds one extra Claude call before calling the exact same retrieval RPCs plain search already uses.

1 extra Claude call (the split)
0 schema changes
4 max sub-questions by default
Reuses reciprocal_rank_fusion()
Composable with hybrid + rerank + expansion
Motivation

The problem in plain terms

A single search — dense (embedding) or keyword — can only point in one "direction" at a time. A question that's secretly two questions glued together confuses it: the search ends up as a blurry compromise between two topics instead of a precise hit on either one.

Example:

Question: "How does soluble fiber's effect on LDL cholesterol differ from insoluble fiber's effect?"
  • This is secretly two questions: (a) "What does soluble fiber do to LDL cholesterol?" and (b) "What does insoluble fiber do to LDL cholesterol?"
  • A single embedding of the whole question ends up as a blurry average of both topics, which can under-match either one — or let whichever topic dominates the sentence bury the other below the retrieval cutoff.
  • The fix: have Claude split it into the two sub-questions, run retrieval separately for each, then combine both result sets before reranking. Now you're guaranteed chunks about both fiber types show up, instead of hoping one combined search happens to surface both.

The same failure mode shows up any time a question bundles distinct nutrients, populations, or conditions into one sentence — e.g. "What are the RDA recommendations for calcium and vitamin D in postmenopausal women?" is really two nutrient lookups sharing one population qualifier.

One combined search"Find me something about fiber and cholesterol in general." — a blurry average of two topics.
Multi-query split"Find me soluble fiber's effect" and, separately, "find me insoluble fiber's effect" — two precise searches, fused.
Diagram

How multi-query splitting fits the pipeline

Splitting runs first, before any embedding or keyword search happens — everything downstream (dense search, keyword search, HyDE's alternative embedding, reranking, parent-chunk expansion) is unaffected by whether a split happened, except that it now runs once per sub-question instead of once. The sub-question list is Claude's own judgment call: an already-atomic question comes back unchanged, so multi-query splitting costs one extra Claude call but never fewer or lower-quality results.

Splitting never changes what a search RPC does — it only changes how many times it's called, and with what text. If Claude declines to split (the common case for a simple question), the whole extra step still runs, but collapses to exactly the behavior plain retrieve_chunks()/hybrid_search() already had.

🔵 One combined search (no split)

What every retrieval method here already does by default — one embedding, one keyword query, one ranked list. Exactly what happens when a question is already atomic, or when use_multi_query is left at its default (False).

"How many grams of protein per kilogram does the RDA recommend?" → 1 search

🟦 Multi-query split

Claude rewrites a compound question into up to MAX_SUBQUESTIONS (default 4) self-contained sub-questions — pronouns like "it"/"the other one" are resolved to their actual subject, so each sub-question can be searched entirely on its own — then every ranked list is fused into one with the same reciprocal_rank_fusion() hybrid search already uses.

"How does soluble fiber's effect differ from insoluble fiber's?" → 2 searches, fused
Reference

Splitting rules, fallback, and how it composes with everything else

Two things this module has to get right: never leave the caller with nothing to search on (even if Claude's response can't be parsed), and reuse — rather than duplicate — the exact fusion logic hybrid search already validated.

Claude's response to the split promptWhat split_into_subquestions() returns
Two or more "SUBQ: ..." lines (question bundles independent needs)split — one string per line, each self-contained, capped at MAX_SUBQUESTIONS
Exactly one "SUBQ: ..." line (question judged already atomic)unchanged — a single-element list containing the original question
No parseable "SUBQ: " line at all (empty reply, malformed output, refusal)fallback — a single-element list containing the original question; a parsing failure never leaves the caller with nothing to retrieve on

A single-sub-question result still goes through reciprocal_rank_fusion() — harmless (the fused order matches the underlying search's own order, just with an rrf_score/sub1_rank key attached), and keeps retrieve_chunks_multi_query()'s return shape uniform whether or not a split actually happened.

How use_multi_query composes with the other ask_question() flags

Combined withWhat happens
use_hybrid=Truecomposes — each sub-question is itself searched with hybrid_search() (dense + keyword, fused), and those per-sub-question fused lists are then fused again across sub-questions.
use_hyde=Trueignored — multi-query needs a single-question retrieval function per sub-question; wiring a HyDE draft per sub-question isn't done here, the same reasoning use_hybrid already uses to ignore HyDE.
use_rerank=Truecomposes — reranking runs after multi-query's fused candidate pool is assembled, exactly as it runs after hybrid search's pool today.
expand_to_parents=Truecomposes — expansion runs last, on whatever chunks multi-query (and rerank) already selected; it doesn't know or care how they were retrieved.

Python API

No SQL migration needed — this only adds one Claude call (to split the question) before calling the exact same retrieve_chunks()/hybrid_search() RPCs, once per sub-question. 

# low-level: split, retrieve, and see the sub-questions used
from reusable_code import split_into_subquestions, retrieve_chunks_multi_query, hybrid_search

subqs = split_into_subquestions("How does soluble fiber's effect on LDL differ from insoluble fiber's?")
# -> ["What does soluble fiber do to LDL cholesterol?", "What does insoluble fiber do to LDL cholesterol?"]

rows, subqs = retrieve_chunks_multi_query(
    "How does soluble fiber's effect on LDL differ from insoluble fiber's?",
    match_count=5, return_subquestions=True,
)                                                              # default retrieve_fn = retrieve_chunks()

# each sub-question searched with hybrid_search() instead of plain dense search:
rows_hybrid = retrieve_chunks_multi_query(
    "...", match_count=5, retrieve_fn=hybrid_search,
)

# end-to-end, composes with hybrid search, reranking, and parent-chunk expansion:
from reusable_code import ask_question
result = ask_question("...", use_multi_query=True)                                                     # split, then plain retrieval per sub-Q
result = ask_question("...", use_multi_query=True, use_hybrid=True, use_rerank=True,
                       expand_to_parents=True)                                                            # full pipeline

Final answer

Claude Sonnet, now grounded in chunks about both fiber types

Soluble fiber lowers LDL cholesterol by binding bile acids in the gut, forcing the liver to pull more cholesterol from the blood to synthesize replacement bile acids. Insoluble fiber has little to no effect on LDL — it does not bind bile acids the same way. Without splitting, one combined search risked surfacing only one fiber type's chunk (whichever the sentence emphasized); splitting guaranteed both sub-questions a fair search of their own, so both mechanisms made it into the fused candidate pool.
